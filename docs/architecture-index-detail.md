# Architecture index — unabridged bullets

This is the verbatim long form of the `## Architecture index` in [../CLAUDE.md](../CLAUDE.md), moved out on
2026-09-07 to keep that file under 40k characters. CLAUDE.md keeps a one-to-three-line version of every
bullet below; when a compressed bullet is not enough, read the matching entry here, then the iteration
doc it names. Per-area narrative detail also lives in [architecture.md](architecture.md).


- **Auth flow** — register/login/refresh/logout/me; `LoginRateLimitFilter` runs before `JwtAuthenticationFilter`.
- **FREE object cap counts LIFETIME creations, not live rows (V107)** — `users.lifetime_project_count` (seeded from the current object count) is the basis, so **deleting a completed/cancelled object can't slip past the cap** (anti-abuse). `LimitService.reserveProjectSlot` locks the user, checks `lifetime >= MAX_PROJECTS`, and increments in the same tx (a delete never decrements); the idempotency check in `ProjectService.create` runs first so an offline replay never re-reserves. `PlanLimitsResponse.projectsUsed` (= lifetime) is what the PWA gate/banner read — NOT the live list length. Permanent delete (`useDeleteProject`, cascade) is offered from the object-row ⋮ **only on a terminal object**, behind a strong destructive `ConfirmDialog`.
- **Refresh tokens** — hashed at rest (SHA-256), rotated (old revoked on use), swept daily; **the PWA must single-flight `/refresh`** or a burst of 401s self-logs-out.
- **Email verification is soft** — `@Async` fail-soft; only `POST /estimates/{id}/share` is gated (403 `EMAIL_NOT_VERIFIED`); email editable only while unverified.
- **Web push** — VAPID, `@Async`, env-gated fail-soft; `deliver()` MUST pass `Encoding.AES128GCM` (legacy `aesgcm` → FCM 403).
- **Client portal is project-level** — `project_share_links` token + `estimates.portal_visible`. A second visibility toggle, `payments_visible` (V93, default false), independently gates the portal's payments card. **The per-estimate `?t=` link is NOT legacy — it is the single-estimate share path** (portal-single-estimate-link iteration): sharing from one estimate's editor mints/reuses that estimate's own link (`estimateShareApi` → `POST /api/estimates/{id}/share`) and never reads or writes the object's portal, so a sibling estimate can't be silently dropped off a link already sent; sharing from the object root / Економіка still publishes a ticked SET onto the object's `?p=`/`?e=` link. `ShareLinkService.create` is idempotent (reuses the estimate's current link; an **expired** one is replaced, since the repository query filters only `revoked`). PWA: one `SharePortalSheet`, the two scopes made mutually exclusive by a discriminated props union (`singleEstimateId` XOR `mode`).
- **Client messages** — one-way inbox (renamed from "questions", V74); entity field `read` vs view JSON key `isRead`; message-link + file attachments + 6-month retention (V75-77).
- **Login rate limit** — `CachedBodyHttpServletRequest` (re-readable body); key `email|ip`; in-memory (single-node only). **All eleven limiters now share one `BucketRegistry<K>`** (review B-22): each used to hold a bare `ConcurrentHashMap` that only ever grew, and for the account-keyed ones that is bounded by the number of masters and merely untidy — but **six are keyed by something a STRANGER chooses** (`email|ip` on login, the IP on register and forgot-password, a portal token), so the map was unbounded by **request content**: the cheapest way to spend this process's heap was to keep logging in as a new address. An entry untouched for **twice its own refill period** (never under two hours) is dropped, and that changes no decision anyone can observe — by then the bucket has refilled to capacity, and **a full bucket is exactly what a first-time key gets**. That equivalence is the entire licence to evict, and it is why the sweep may be as crude as it is; the refill period is **passed in rather than assumed**, because the login and portal windows are configuration. The sweep is **opportunistic** — it runs on a call that finds one due, not on a scheduler: it costs a pass over a map that is small by construction, a limiter nobody is calling has no growth to contain, and there is no new dependency and nothing to shut down. `ageAll()` is package-private so `BucketRegistryTest` can age the map without waiting two hours, and it sets the next sweep to `Long.MIN_VALUE` rather than 0 — `System.nanoTime()`'s origin is arbitrary and may be negative, so a literal zero would not reliably read as «overdue». Still **process-local**, like everything it replaces: the multi-instance store remains an open question and this changes nothing about it.
- **Signed estimates are immutable** — mutate/delete → 409 `ESTIMATE_SIGNED`; owner-only `reopen`; `@Version` optimistic lock (V23). `reopen` is fully live server-side but **hidden from the UI** (`REOPEN_ENABLED = false`, independently declared in both PWA locations that used to show it) — the master's call, code kept for a possible return. **A signed estimate lives only in the Економіка tab** (economy-rework iteration) — the Кошторис tab shows DRAFT/SENT/REJECTED only (`ProjectDetailPage`'s `activeList`); `EstimateService.reopen`'s mechanics are factored into a shared `applyReopen(estimate, reopenedBy)` (owner-facing `reopen` still uses it). **A signed parent is NOT auto-reopened when its duplicate is signed** (acts iteration, was the old economy-rework behavior): `PublicEstimateService.doSign` now sets `parent.countInEconomy = false` (keeps the signature — it's a historical fact, and once work acts reference a SIGNED estimate, reopening it could pull it out from under an act already sent) and stamps `estimates.superseded_by_estimate_id` (V95) with the duplicate's id. The parent stays a SIGNED panel in Економіка, just uncounted in the summary; the supersede banner is suppressed for DRAFT rows in the PWA (only legacy already-reopened drafts still carry the flag there). The flag clears on edit (via `requireNotSigned`, the one guard all 8 write paths share), re-sign, or an explicit dismiss endpoint.
- **Work acts (`work_act`/`work_act_item`, V104)** — a document built from a signed estimate's positions, signed separately (acts iteration). All line fields are **frozen copies** (name/category/unit/price + `cumulative_before`); `estimate_item_id`/`estimate_id` are `ON DELETE SET NULL` so a sent act reads identically after the estimate is edited/deleted. Invariants in `WorkActService`: **one open (DRAFT/SENT) act per object** (409 `WORK_ACT_OPEN`), a **FINAL** act closes it (409 `WORK_ACT_FINAL_EXISTS`), **signed = immutable** (`requireNotSigned`, 409 `WORK_ACT_SIGNED`), delete only DRAFT/REJECTED. **Numbering is continuous per master** (never reset per year — PLAIN «7» would else collide under `UNIQUE(user_id, number)`); `create()` is non-`@Transactional` and retries `WorkActCreator.attempt` (public, own tx) on a lost number race; `WorkActResponseFactory` builds the response inside that tx. **Progress is never denormalized** — Σ quantity over SIGNED acts (`sumSignedQuantitiesByEstimateItem`) feeds both the progress endpoint and each new act's frozen `cumulative_before`; `exceedsEstimate` is computed live, the master decides. **Signing with additional (off-estimate) lines** creates a SIGNED, counted, non-shared `Estimate.kind = ADDENDUM` («Додаткові роботи до акта № N», amounts via `EstimateMath`) in the same tx so «Прийнято актами» never exceeds «За договором»; ADDENDUM is filtered out of `listForProject` (Кошториси tab + pickers). `Feature.WORK_ACTS` (temp-FREE, like OBJECT_ECONOMY/MEASUREMENTS). **The estimate read path surfaces progress too**: `EstimateItemResponse.closedByActs` (nullable; second `from(item, closed)` factory, plain `from(item)`→null so no fan-out) is a per-line Σ over SIGNED acts, built in `EstimateService.toResponse` **only for a SIGNED estimate** (one `sumSignedQuantitiesByEstimateItem`, no N+1) — drives the estimate board's «✓ закрито»/«done/total» chip; a DRAFT act never colours a line (same rule as the running total). PWA act UI is the `/acts/:id` `ActEditorPage` (tick = full remainder, exceeds→convert-to-additional), `ActsSection` (blocked when an act is open or a FINAL exists — `actCreateBlock` mirrors `WorkActCreator`), and «Згенерувати акт» on the economy panel ⋮. **«Новий акт» creates NOTHING** (receipts-batch round 4 — «може випадково натиснули», and a number is permanent): `useNewAct` only navigates to the **static** `/acts/new?project=…&from=…&scope=…` (registered above the dynamic `/acts/:id`), whose defaults ride the query string because there is no row to read them from. In the editor `isNew` (`id === ''`) skips the load gates, seeds off the query string, forces `dirty` true (leaving always asks, with its own «акт не створиться» copy), and hides everything that addresses a row (number, status badge, 🔗 share, PDF, delete, `ActReceiptsSection` → «Збережіть акт, щоб додати чеки»). `persist()` is the ONE door «Зберегти» and «Підписати» share: on a new act it `create`s (X-Entity-Uuid in a ref, so a double tap can't double-number), `replaceItems` on **the id create answered with**, then `navigate(routes.act(id), {replace:true})` past `skipLeaveGuard`. `useActsInvalidator(projectId)` takes the id at call time for exactly that (`useActWriter` delegates to it).
- **Act portal (`ShareLinkKind.ACT`, `?a=`, V105)** — a **fourth** share-link kind, deliberately NOT folded into read-only ECONOMY (which must never let the client sign). One link = one act: `project_share_links.work_act_id` (FK, invariant CHECK `(kind='ACT')=(work_act_id IS NOT NULL)`). Owner side is `ProjectPortalService` act trio (`actState`/`updateAct`/`sendActEmail`; publish flips DRAFT→SENT + mints the act's link) on `WorkActController` `.../{id}/share`; public side is `PublicActPortalController` → `PublicActPortalService` (`/api/public/act/{token}` view/sign/question/pdf). **Defense-in-depth: only SENT/SIGNED served** (a DRAFT is 404 even with a valid token — the `economyVisible` lesson). Sign records signer name/phone/ip/UA, stamps SIGNED, computes **`doc_hash` = SHA-256 of the canonical (unstamped) PDF** (`WorkActPdfService.PdfModel.docHash` re-stamps it on download), pushes the master + emails the client a PDF copy (`EmailService.sendSignedActCopyEmail`, Resend attachment) — both fail-soft. Honest wording «Підтвердити приймання робіт», never a legal-equivalence claim. `PublicActView` is a fresh client-safe DTO (in `PublicEstimateIsolationTest` roots). `static/portal/index.html` has a `?a=` `renderAct` branch (before `adaptLegacy`).
- **Works axis in economy (FREE-visible)** — `ObjectEconomyResponse.acts` (`ObjectEconomyActsResponse(contracted, acceptedByActs, received)`), computed **unconditionally** (not behind `internals`) in `ObjectExpenseService.economy`: `contracted = sumIncomeCounted` (== `payments.contractedTotal`), `acceptedByActs = sumSignedActLineTotals`, `received = PaymentReceiptRepository.sumByProjectId`. PWA `ActsAxis` is a PaymentStrip twin; the balance line (`acceptedByActs − received`) flips «Невідпрацьований аванс»/«Заборгованість замовника»/«Розрахунки збігаються» by sign; `(i)`-popups (`acceptedInfo` interpolating the not-yet-accepted remainder, `clientDebtInfo`, `unearnedAdvanceInfo`) name the two different debts. **INVARIANT — numerator and denominator are counted over ONE estimate set** (acts-fix): both `sumSignedActLineTotals` and `sumIncomeCounted` count only SIGNED + `count_in_economy = true` estimates, plus off-estimate additional lines (`estimate_id IS NULL` — their ADDENDUM is itself counted). So «Прийнято актами» ⊆ «За договором», never past 100 %. Enforced three ways: `WorkActService.progress` skips `!countInEconomy` estimates; a write guard (`requireCountedEstimateLines`, 400 `WORK_ACT_ESTIMATE_EXCLUDED`) rejects an excluded-estimate line; and **both** sign paths create the ADDENDUM via the shared `ActAddendumCreator` (the portal path used to skip it — acts-fix). Don't drop the `IS NULL` branch or the `count_in_economy` filter from either query without breaking this. **An ADDENDUM panel in Економіка therefore carries no ⋮ at all** — both its actions were dead ends on it: «Згенерувати акт» would open a scoped editor with no positions (`progress` skips ADDENDUM — that money IS an act already), and «Не враховувати цей кошторис» is answered 409 `ESTIMATE_ADDENDUM_LOCKED` by `EstimateService.setCountInEconomy`, since the act’s off-estimate lines and re-billed receipts count in «Прийнято актами» regardless of the flag.
- **The economy progress strip is ONE component, and it lives in THREE places (green-progress-strip, no migration)** — «щоб та полоска … потехеньку зеленішала». **Colour is a POSITION, never a verdict**: the brand→success gradient always spans the whole TRACK (`background-size: {(100/pct)*100}% 100%` on a fill that is only `width: {pct}%` wide), so the fill is a WINDOW onto it — 30 % shows only orange, 90 % shows a green tail, no point ever changes colour. The rejected alternative (interpolate ONE flat hue by percent) paints a half-done object entirely in the muddy olive between the two tokens, which on a money screen reads as a warning; here that olive is only ever the leading edge of a mostly-orange bar. Drop the `background-size` and you silently get the hue-interpolation that was rejected. **100 % is a separate state, solid `bg-success`, no gradient.** The PWA’s three copies at the time (`PaymentStrip` + `AxisStrip`×2 — the latter used to carry a literal `{/* twin of PaymentStrip */}` comment) are now the single `components/ProgressStrip.tsx`; `AxisStrip` takes `total` instead of a precomputed `pct`. **Two of those three are left**: the «Платежі» card’s strip went on 2026-09-21, because it drew the same two figures as the works axis line directly above it — both read `sumIncomeCounted` for the denominator and the sum of the object’s receipts for the numerator, so the two bars could never disagree, and the master counted three bars on one screen and asked what the difference was. **The copy outside the bundle cannot be shared** — `static/portal/index.html` is a standalone page in the OTHER repo that never loads the PWA bundle and has its own palette, so `.paybar-fill` hand-copies the rule and both files name each other in a comment: **change one, change the other in the same commit.** Same pass killed a `Math.min(100, …)` that capped the LABEL as well as the bar, so an overpayment (a real state — see `PaymentOverflowResolution`) read as «100 %»: `progressPct()` is **uncapped** and feeds the label + `aria-valuenow`, only the width clamps. [docs/iteration-green-progress-strip.md](docs/iteration-green-progress-strip.md).
- **Act «ДОВІДКОВО» reference block (acts-fix, V106)** — three object-wide money rows (виконано з початку / за кошторисами / залишок), NOT a per-line table; sourced from the SAME queries as the works axis via the shared `ActCumulativeCalculator`, so PDF and app never disagree. **Default OFF** (`show_cumulative` V106 default `false` + data-cleared; `WorkActCreator`/PWA `useNewAct` both send false) and shown only **from the 2nd act** (`existsByProjectIdAndStatusAndIdNot(..., SIGNED, ...)`). The figures are live and object-wide, so the block is **excluded from the canonical (hashed) render** (`PdfModel.cumulative = null` at hash time) — a later signing must never invalidate an earlier act's stored `doc_hash`; the block is thus a live reference, deliberately outside tamper-evidence.
- **Acts follow-ups (acts-improvement, V108 `work_act.title`)** — (1) **Optional `title`** (varchar 120, «Штукатурні роботи»), frozen on sign like every act field; PWA suggests it from the object's estimate categories and auto-fills when all picked lines share one category. On `WorkAct`/`WorkActResponse`/`PublicActView`. (2) **Owner status moves** — `PATCH /api/acts/{id}/status` → `WorkActService.changeStatus`, allowed set ONLY `SENT→DRAFT` (recall) / `SENT→REJECTED` (client declined) / `REJECTED→DRAFT`; anything else (incl. touching SIGNED) is 409 `WORK_ACT_BAD_TRANSITION`, and `REJECTED→DRAFT` re-checks the one-open-act rule (409 `WORK_ACT_OPEN`). (3) **`ActSignedCopyService`** — the docHash stamp + client PDF email, shared by BOTH sign paths; **fixes that offline signing (`signOffline`) previously produced NEITHER** (no tamper stamp, no client copy) — so the CLAUDE note above about the portal path emailing a copy now applies to offline too. (4) **`QuestionRateLimiter`** — client questions on ANY public portal (`?t`/`?p`/`?e`/`?a`) are rate-limited keyed on IP+token (writes: stored message + push to the master), separate from the blanket 30/min `PortalRateLimiter` read cap. PWA also gained `useLeaveGuard` (unsaved-act-edit guard) and `openPdfTab` (iOS-Safari-safe PDF open).
- **Act receipts — «Чеки та рахунки» (act-receipts, V110 + V111)** — materials the master paid out of pocket, re-billed on one act. `work_act_receipt` (singular; label / `amount > 0` / `issued_at` / `storage_key`) + `work_act.receipts_to_expenses` (default true). **The photo is MANDATORY** (round 2, 400 `WORK_ACT_RECEIPT_PHOTO_REQUIRED`) — a receipt row with no paper behind it is just a number anyone could type; `storage_key` stays nullable only for V110-era rows. Six endpoints on `WorkActController` (multipart add with the photo, text-only update, delete, owner-authenticated photo stream, and `POST …/receipts/recognize`) — all three writes behind `requireNotSigned`, so receipts freeze on sign like every other act field. `WorkActResponse` carries `receipts`/`receiptsTotal`/`payable` (= works `total` + receipts − `advanceOffset`, floored at 0). **The ⊆ invariant extends to them**: receipts are money no signed estimate promised, so on sign they go into the act's ADDENDUM via the shared `ActAddendumCreator` (both sign paths) and `sumSignedActReceipts` feeds `acceptedByActs` alongside `sumSignedActLineTotals` — add one without the other and «Прийнято актами» passes «За договором». `receipts_to_expenses` posts each receipt as a MATERIALS/RECEIPT `ObjectExpense` on sign so pass-through money can't inflate `Прибуток`; switching it off still bills the client, just posts nothing. Portal: `PublicActView.receipts` + `PublicActPortalService.receiptFile(token, receiptId)` (token-scoped, never `/api/files/**`), `?a=` `renderAct` section with tappable thumbnails. PDF: the receipts block is **inside** the canonical hashed render (unlike the live, object-wide «ДОВІДКОВО» block, which is excluded) — receipts are frozen act content, so they belong to the tamper-evidence. PWA `ActReceiptsSection` saves each receipt immediately (a multipart photo can't ride the header's JSON «Зберегти»); only `receiptsToExpenses` sits in the editor's dirty snapshot. **`ActEditorPage` now opens with a sticky TOP bar** (back · number · status · 🔗 share · Зберегти) — master feedback that Save lived only in the FAB, off-screen; a bottom bar was impossible (mobile nav ≈60 px + FAB at `bottom-20`), and the FAB sheet carries the same 🔗 «Поділитися з клієнтом» row (round 3 — the top bar scrolls away on a long act, which is exactly where the master reached for it). Both open the same `ActShareSheet` for the already-open act. **Round 2 (V111) added three things.** (1) **Recognition** — `POST /api/acts/{id}/receipts/recognize` reads label/date/total off the footer (`AiFlow.ACT_RECEIPT`, haiku) and **nothing else**. It used to have a second, PRO-gated `withItems=true` mode reading the item table; that went with the transfer it fed (**round 4**, see below), and with it the last gate on this path — **reading a receipt for an act is now free, full stop**. It is still **the first LLM call a FREE plan can reach** and it persists nothing, so no business counter bounds it — `ReceiptScanRateLimiter` (Bucket4j, per account, `app.rate-limit.receipt-scan.max-per-hour`, default 30, in-memory/single-node like the others) does, answering 429 `error.rate.receipt-scan`. It only PREFILLS what the master confirms; an `AiExtractionException` is a soft `failed()`, never a blocked flow. **`recognize` is NOT `@Transactional`** — a vision call must not pin a pooled connection; ownership + not-signed run in their own short transactions up front (same shape as `ReceiptImportService.parse`). (2) **`itemized` — now LEGACY, and still load-bearing** — a receipt whose positions were carried into the act as its own LINES bills the money that way, so it is excluded from `receiptsTotal`/`payable`, the ADDENDUM rollup, `sumSignedActReceipts` and `sumByWorkActId` (both queries carry `AND r.itemized = false` — drop it from one and the money is billed twice), and from the PDF/portal subtotal. **The expense posting deliberately takes ALL receipts**: the master paid either way, only the billing path differs. **No new row can get the flag since round 4**, but the column, the field and every filter STAY: rows created that way may be frozen into a SIGNED act, its `doc_hash` and its ADDENDUM, and must keep reading exactly as they were signed (`WorkActIntegrationTest.markItemized` sets it on the row directly for that reason). (3) **`work_act.show_receipt_photos`** (default true) — PDF-appendix-only toggle; the receipts money table always renders and the portal always shows the photos. **Round 3 (the master's first real receipt) fixed three things at once.** (a) The item pass was made to share `EstimateExtractor`'s tuned prompt + schema verbatim — moot since round 4 removed that pass, and both are `private` again. (b) Dates are parsed in the shapes paper actually prints (`dd.MM.yyyy`, `dd/MM/yyyy`, `dd-MM-yy` — the ККМ footer's `DD-MM-YY HH:MM:SS № NNNN`), not ISO only, and **only a FUTURE date is rejected** — the old "older than 3 years → null" rule blanked genuinely old paper, which is exactly what a master photographs. (c) The real cause of «нічого не зробило» was on the PWA side: the LLM-timeout rule in `api/client.ts` matched only URLs ending in `/parse`, so `…/receipts/recognize` inherited the 12 s fail-fast write default and aborted mid-call (the small footer pass usually squeaked in, the full item read never did) — it now matches `/recognize` too. **A new LLM verb must be added to that rule or it inherits the same silent failure.** **Review follow-up B-28 — a SENT act must stay SIGNABLE.** While an act is SENT the client can sign it at any second, and `ActReceiptCompleteness` refuses a signature over an unpriced receipt (400 `WORK_ACT_RECEIPT_UNPRICED`) — so nothing stopped the master pricing a receipt DOWN to zero on an act already in the client's hands, and the client tapped «Підтвердити приймання» and got an error that was the master's to fix and that nothing on his screen explained. **Only `update` refuses it, and that narrowness is the point**: `add` still accepts 0, because a zero there is the receipts-batch state («save the photo first, price it later») **and** what an offline queue replays hours after the act went out — refusing it there would trade an awkward window for a lost photo. An explicit edit to zero has neither excuse, and V108's door is always open: move the act back to DRAFT, fix it, re-send. **No `unpricedReceipts` field was added** — `WorkActResponse.receipts` is fully populated on both the list and the get, so the PWA already counts and badges them; what it gained is a **different sentence on a SENT act** («Акт уже в клієнта, і поки сума не вказана, він не зможе його підписати»), because the generic «не можна надіслати чи підписати» is not what is happening once it has been sent. Same round, **B-29**: `saveReceiptCopy` (the second copy into «Чеки») checked the photo LIMIT but never the `PHOTO_REPORTS` FEATURE — harmless while FREE has it, and wrong the moment that changes, since it was the only door into the gallery that never asked. And **B-31d**: the PDF's photo caption printed gross `amount()` while the money table billed `billedAmount()`, so one receipt with a partial return (V115) read as two different figures in one document — with the **bigger** one under the photo that proves it; the caption now prints what is billed, and both figures when there is a return, because the paper itself says the gross one: «1 500 (на чеку 2 000, повернуто 500)».
- **Fiscal QR fast path (`service/fiscal/`, fiscal-qr iteration, no migration)** — every Ukrainian fiscal receipt prints a QR carrying `fn`/`id`/`date`/`sm`; reading it beats reading the paper, exactly and with no model call. A **separate** «🔳 Зчитати QR» option on BOTH receipt dialogs (estimate import + act receipts) — the photo routes stay untouched beside it, because a hand-written slip or a faded ККМ tape carries no QR. `FiscalQrService.read` is a ladder that **degrades, never fails**: unreadable payload → not recognized; the (undocumented) ДПС cabinet lookup unreachable/refusing → **still recognized** on the QR's own total + date, no positions; positions that don't sum to `sm` within **0.02** → dropped wholesale, meta kept (the decoder is *guessing* the integer scaling of an undocumented `checkXml`, so `sm` is the independent witness — a wrong price the master signs is worse than a missing one). `FiscalCheckXml` is deliberately tolerant (both `ROW`/`P` layouts, several spellings per field, attribute *or* child) and XXE-hardened; bytes go in raw so the windows-1251 declaration decides. `app.fiscal-qr.base-url` blank = lookup disabled (that's how `application-test.yml` keeps tests off the tax service). Lines are normalized through the same `ReceiptLines.toParsedItems` as a photo read, so units are flagged identically. Entry points: acts `POST /api/acts/{id}/receipts/qr` (**soft** — total+date alone are worth having; it took a `withItems` tick until the act-side transfer was removed on 2026-08-28, and now never reads positions at all, so it never dials out), estimates `POST /api/estimates/{id}/receipt-items/qr` (**hard** 400 — that flow exists only to make lines, an empty review would read as «чек порожній»); both share the existing `ReceiptScanRateLimiter`. **Everything the QR hands back is FREE, positions included** (master decision, 2026-08-23) — no model runs, so there is nothing to gate. Consequence: `ReceiptImportService.commit` **lost its `RECEIPT_IMPORT` gate** (appending lines was never the paid capability — reading a receipt PHOTO is; `commit_isNotAPaidCapability` pins it), the PWA's «перенести позиції» tick is free to toggle with the upsell moved onto the **photo** item-read, and the estimate editor's 🧾 FAB no longer gates at all. PWA: `lib/qr.ts` (native `BarcodeDetector` preferred, **`jsqr` fallback for iOS Safari**, a miss/throw is just `null` — one bad frame must not end a scan) + `QrScanSheet.tsx` (camera lifetime only; picked-photo fallback offered in BOTH states, not only on failure; a non-fiscal code is named on the spot via `looksFiscal`). **The act receipt photo stays MANDATORY** — a fiscal code is not a photograph of the paper. `/qr` had to join `/parse`+`/recognize` in `api/client.ts`'s long-timeout rule (it waits on the tax service, not on a model — same silent mid-call abort otherwise). Full detail: [docs/iteration-fiscal-qr.md](docs/iteration-fiscal-qr.md). **First live paper found two bugs the whole suite could not see, because both live below the top rung and the tests never dial out** (both fixed, both now pinned): (1) `lookup` handed its already-encoded URI to `RestClient.uri(String)`, which reads a String as a URI **template** and encodes it AGAIN — the space in `date` arrived as `%2520`, ДПС answered «Помилка обробки запиту», and EVERY scan silently degraded to meta-only. Build the URI with `.encode().build().toUri()` and pass the `URI`; the same rule applies to any other outbound call in this codebase that pre-encodes. - **A receipt at the till is a RECEIVABLE, not a cost (V129 «Чеки обʼєкта»)** — this is the decision the whole table encodes. In this trade the material money is mostly the **client's**, so `project_receipt.reimbursable` defaults to **TRUE** («клієнт відшкодовує», master's ruling), a reimbursable receipt writes **nothing** to `object_expenses`, and only an explicit «це моя витрата» creates a MATERIALS/RECEIPT `ObjectExpense` whose id lands in `project_receipt.expense_id` — flipping back deletes it. The other way round is the obvious one and it is wrong: booking material the client paid for as the master's cost makes `Прибуток` quietly wrong for the MAJORITY of masters, and the mistake is invisible because the number still looks like a number. This way the common case is free of decisions (camera → сума → зберегти, two taps, nothing decided) and the one economic judgement sits behind a single tap in the minority case. `expense_id` is `ON DELETE SET NULL` so deleting the expense by hand from the journal just unlinks the receipt, and a CHECK (`expense_id IS NULL OR reimbursable = false`) stops a later edit leaving a dangling bill. **V126's rule survives**: money still enters the economy only through a receipt, and now only through a deliberate one. **Why a SECOND table beside `work_act_receipt`**: that one is a receipt ON A DOCUMENT — it exists to be re-billed on one act and is frozen into that act's `doc_hash`. The paper in the master's hand at the merchant belongs to no act yet; he buys before he signs, usually before an act exists at all, and filing it against the OBJECT is what lets the till involve no document choice and no economics. Merging them would mean either a nullable `work_act_id` on a table whose rows are hashed into signed documents, or an object receipt inheriting the act's not-signed guard, which an object has no equivalent of. Everything else is the receipts-batch shape verbatim: photo **MANDATORY** (400 `PROJECT_RECEIPT_PHOTO_REQUIRED` — a receipt row with no paper behind it is a number anyone could type); photo saved first, priced later, so `amount = 0` is a legal intermediate state and **nothing gates on it here** (unlike an act, an object receipt is part of no document anyone signs, so a priceless one costs nobody anything — the screen just carries `unpricedCount`); create idempotent on `X-Entity-Uuid`, or a retried upload over a weak connection bills the same material twice; `recognize` reads the ALREADY-STORED photo, is QR-first and vision-second, persists nothing, never fails hard, and is not `@Transactional`, with the QR path on its own `QrScanRateLimiter`; positions are never read into anything (the money on a receipt is its total); `MAX_RECEIPTS = 100` per object (higher than an act's 50 — an act covers one stage, an object the whole renovation), `MAX_PHOTO_BYTES = 8 MB`, and a blank label is named «Чек №N» by the SERVER. **`fiscal_fn` + `fiscal_id` are a WARNING, never a unique index** — they come off the printed fiscal QR and identify the physical paper exactly, so the same slip photographed twice can be SPOTTED; but the photo is saved first and read afterwards, so the identity is only known on a later PATCH, and a unique index there would turn a duplicate into a failed save of a photo already taken. - **A tap is lost to the BROWSER, not to a handler (touch-targets)** — «не можливо анселектнути чекбокс, то просто мука… і так само з деякими кнопками, наприклад, на порталі клієнта кнопка Підписати, з 5-того разу спрацювало натиснути»: two surfaces, two codebases, one symptom — a control that answers roughly one tap in five, and one of them is the single action the portal page exists for. **What it was NOT is worth writing down, because it is where the first hour goes**: every handler on both paths is correct. The shopping tick is a 56 px `<button>`, a SIBLING of the row body rather than nested in it, and `disabled` is `archived` — not a pending mutation, so no write can lock it; `useShoppingActions.toggle` reads which way to flip off the CACHE, not off the render closure, and patches optimistically on both the online and the queued path; the portal's `[data-sign]` handler is bound on every render, and the delegated `document` click listener that dismisses the info popover neither stops propagation nor cancels anything. Nothing in application code was dropping these taps. The browser was. **Two causes.** A press that lands on TEXT starts a selection, and the `click` is then **never dispatched** — both controls carry their own label (the `✓` inside the tick's span, the word «Підписати» inside the button), and on Android and iOS a press held a moment too long over text begins a native selection and then the callout menu. A master in a work glove presses slowly: he gets nothing, presses again, gets nothing, until one tap happens to be quick enough. That is the whole complaint, and it is **invisible to every test** — the markup is right, the handler is right, the event simply never fires. And **double-tap-to-zoom makes the retry worse**: both pages are pinch-zoomable by design, so the browser holds a tap briefly to see whether a second is coming, and the natural reaction to a missed tap — tap again, immediately — is exactly the gesture that reads as a zoom rather than two clicks. The fix is `user-select: none` + `-webkit-touch-callout: none` + `touch-action: manipulation` on everything that is tapped, in both repos: the PWA's copy is a block in `src/styles/index.css` **inside `@layer base`**, so a Tailwind utility still wins where a surface needs the other behaviour (`touch-none` on a drag grip is the live example); the portal, message and admin pages each carry the same block in their own `<style>`. **Mirrored pair — change one, change the other**, exactly like the green progress strip. ⚠️ **Tailwind silently DROPS an at-rule nested inside `@layer base`**, so a base rule must never be wrapped in a `@media`. **Three things ride along.** `future.hoverOnlyWhenSupported` in `tailwind.config.js`, and `@media (hover: hover)` around the portal's hover rules: a touch device has no hover but FAKES one, so the last-tapped control keeps its hover look until something else is tapped — and «it still looks pressed» is precisely how the master decides his tap did not land; `:active`, which a touch really does drive, carries the feedback instead. `Button` gained `min-h-11` (44 px — padding alone left it a couple of pixels short). And the portal's 18 px ⓘ dot and its popover ✕ grew an invisible 44 px hit area via `::after`, since they sit inline beside a heading and cannot simply be made bigger. One behaviour change came with it, in `CatalogAutocomplete`: a suggestion used to be picked on `onMouseDown` + `preventDefault()` for every pointer, but on a phone `mousedown` is not a press at all — it is a compatibility event synthesised after the touch has ended, dropped whenever the browser reads the gesture as something else, and cancelling it also cancelled the `click` that would have been the fallback; the mouse keeps its pre-blur path (guarded on `pointerType`) and touch falls through to a plain `onClick`, which fires for a real tap and never for a scroll, so dragging the list to read it no longer risks picking a row. **The follow-up is the other half of the same rule: `user-select` INHERITS.** Each client-facing page wraps its field in a bare `<label>`, so `none` reached the `<input>` inside it, and on iOS Safari an inherited `none` fights the caret — the field focuses, the keyboard opens, and placing the caret inside what is already typed does not work. Inputs (bar the button-like types) and textareas **opt back in explicitly**, in all three server pages and in the PWA's `src/styles/index.css` — the same mirrored pair. **Why tests read the SOURCE as text**: a base-layer CSS rule has no component to render and no behaviour to assert in jsdom, and its failure mode is that everything looks perfect while the button misses taps — so it is asserted against the FILE, the trick `UnitRenderCoverageTest` and the PWA's `swUpdate.test.ts` already use: `PortalTouchTargetsTest` here (three assertions, the opt-out included — losing that half is invisible on screen and shows up only as a client unable to correct a typo in their own name), `src/styles/touch.test.ts` there. **Left open:** 36 px icon buttons (`h-9 w-9`, the ← chrome in ~15 screens) are under the 44 px floor — not part of the report and a layout change in every one of them; and Android's back-gesture strip runs down the left edge where the shopping tick sits ~18 px in, so a gloved press that drifts horizontally can be eaten by the system before the page ever sees it — fixing that means moving the tick, which is a design decision. Two rules follow: **every write endpoint answers with the template it actually wrote, whose `id` may differ from the one in the URL** (the PWA's `adoptDetail` re-keys the query cache onto it — key it under the id you sent and the next refetch hands back the pristine default, so the edits look like they vanished), and **addressing the default afterwards keeps resolving to the same copy** (which is what makes a sequential batch of adds, and an offline replay of ops that all name the default, safe). **Delete on a default is a HIDE** — the override row with `forked_template_id = NULL`, undone by `POST /api/estimate-templates/restore-defaults` (offered unconditionally in the PWA: which defaults are hidden is not something the device can know); the FK is `ON DELETE SET NULL` so deleting the fork later leaves the default hidden, not silently restored. Reorder is `PUT …/items/order` with the **whole** order (`TemplateItemsOrderRequest`, mirrors `EstimateService.reorderItems`) so a replay is idempotent; the PWA queues it under its **own** `templateItemOrder` outbox entity — coalescing keys on entity+entityId+type, so filing it as an `estimateTemplate` update would let a drag swallow a queued rename. A template position still carries **no price** (`TemplateItemRequest` = name/type/unit) whether typed or picked from the catalog. **The PWA editor is EXPLICIT-SAVE** (PWA 1.23.4) — unlike the estimate board, it holds a local draft and writes nothing until «Зберегти», which sits at the TOP next to the name (a sticky bottom bar was tried first, on the `ActEditorPage` reach argument, and rejected by the master — down there it reads as a twin of «Додати позицію»), is enabled by ANY difference incl. the order, does NOT close the sheet (it is a checkpoint, and the sheet must stay open to follow the fork the server just answered with), marks every row that differs from the server green (`unsaved` — DERIVED from draft-vs-baseline, so it needs no state and clears itself on save; NOT the estimate board's timed `touched` set, which that board needs only because it writes immediately) and scrolls a just added/edited row into view (`scrollRowIntoView` had to learn about scroll CONTAINERS for this: inside a `Modal` the page is frozen, so asking `window.scrollY` "did anything move" always said no and fired the instant fallback over a running animation), and replays the diff as rename → removals → edits → adds → **order last** (an add appends, so the drag speaks last); a dirty close asks save/discard/cancel. On partial failure the landed ops stay, the baseline re-seeds from the last SUCCESSFUL answer, and a landed add takes the server id so a retry cannot double-add.
- **`catalog_update_notices` is a queue, not a slot (V94)** — one row per notice-worthy event, `kind` (`COUNT`/`PRICE_DRIFT`) discriminates the shape (CHECK-enforced: each kind carries only its own fields); dismiss/accept are id-scoped, never "the" implicit notice. A master's own catalog price changes ONLY on `accept`, and only if it still equals the notice's `old_price` — never a silent overwrite.
- **Community prices (`price_insight_candidate`, V94)** — weekly job aggregates a two-level median off masters' own ESTIMATE lines (not their catalog, which drifts less): per-master median in SQL (`EstimateItemRepository.aggregatePerMasterWorkPrices`, `percentile_cont`), IQR-trim + cross-master median in Java (`PriceInsightMath`, no Spring dependency), **min 3 masters** survive the trim. `PRICE_DRIFT` (key matches a default) vs `NEW_POSITION` (doesn't — merges into the existing `AdminCatalogInsightsService.newPositions()`, not a new screen). Admin `apply` only updates the shared `catalog_templates` row + queues notices — a master's own price never changes until they personally accept.
- **Custom trades (V91)** — `user_trade` (id/name/sort per master) has no reference catalog by design; `catalog_items`/`estimate_templates` (own only) get a nullable `custom_trade_id` FK, `ON DELETE SET NULL`; invariant on both tables: `custom_trade_id IS NULL OR trade = 'OTHER'` (a custom-trade row is always OTHER underneath, never a bare system trade) — deleting the custom trade drops it to plain "Інше" for free, no app-level UPDATE. `CatalogTemplate`/`TemplateTradeOverride` untouched — a system default can never carry one (DB CHECK also pins `is_default = false`). - **«%» is a share OF something (V88)** — base `POSITION`/`TOTAL` (per-type: works vs materials), `MANUAL` retired; **`line_total` is STORED** (server-authored, never from a request); only a `TOTAL` percent may be negative (+/− toggle, V89).
- **Mirrored formulas — change BOTH sides together** — `EstimateMath.recalculate` ↔ `useEstimate.recomputeLines` (percent pass); `MeasurementCalc` ↔ `measurementCalc.ts`.
- **A request DTO is a CONTRACT with the other repo, and nothing but this snapshot enforces it** — the bug it exists for: V135 added `boolean materialRefund` to `PaymentReceiptRequest`, nothing told the other repository, whose `src/api/types.ts` is written **BY HAND**; its interface never grew the field, TypeScript stayed perfectly happy, and **the master could not record a payment for weeks**. Neither repo's tests could see it, and that is the point — the backend's tests BUILD the request records in Java, so Jackson never runs; the PWA's MOCK the api module, so the body is never serialized; and nothing at all read both sides. `RequestContractSnapshotTest` freezes every `*Request` record's SHAPE — field name, coarse type, and whether the CLIENT must send it — into `src/test/resources/contract/request-dtos.json`, so changing a DTO goes red **in the same commit that changed it**, with a failure message naming the PWA file that has to move with it. Refresh it with `./gradlew test --tests '*RequestContractSnapshotTest' -Dcontract.update=true` — the flag is handed to the forked test JVM explicitly in `build.gradle.kts`, because **Gradle does NOT pass system properties down**. Then **copy the file to `majstr-pwa/src/api/contract/request-dtos.json`** — mirrored pair, change one change the other — where `src/api/contract.test.ts` checks the hand-written interfaces against it with three rules: we may never declare a field the backend lacks, we must declare every field it REQUIRES, and the types must agree; a field the backend merely ACCEPTS may be omitted, or the guard cries wolf. Two design choices carry it. **Coarse types on purpose** — the far side is TypeScript, which cannot tell a `UUID` from a `String` or a `BigDecimal` from an `int`; recording Java's exact types would churn the snapshot on changes the PWA cannot observe, and a guard that cries wolf gets deleted. What matters there is only: does the field exist, is it string/number/boolean/array, and may it be left out (`UUID`, `LocalDate`, `Instant` and every enum cross the wire as strings; a primitive is never «required», since an omitted one takes its Java default — the other half of the same `fail-on-null-for-primitives` bug). And **`required` reads the FIELD and the CONSTRUCTOR PARAMETER, never only the record component**: `@NotNull` does not list `RECORD_COMPONENT` among its targets, so javac propagates it to the backing field and the canonical constructor's parameter and leaves the component bare — the first draft looked only at the component, reported **all 80 DTOs as fully optional**, and would have gone green forever. A contract claiming nothing is required is worse than no contract at all, which is also why the test asserts the scan actually REACHED something (`containsKey("PaymentReceiptRequest")`, `hasSizeGreaterThan(50)`) — a sweep that finds nothing freezes an empty contract and guards against nothing, the exact way the PWA's update banner stayed broken for a year. Pure reflection, no Spring context: this must be the cheapest test in the suite so nobody is ever tempted to skip it, and the JSON is rendered by hand so the file's formatting is owned here and cannot shift under a Jackson upgrade.
- **Estimate line order** — explicit reorder; `EstimatePdfService` mirrors the grouping (change both or the PDF disagrees).
- **One estimate from several templates, and only the POSITIONS he ticked** — concat + dedup by lowercased name; estimate limit checked once. The picked bundles used to ride a `?ids=` query param beside the body; a per-bundle subset cannot travel in a query string without inventing an encoding, and splitting «which bundles» from «which of their positions» across query and body would be two halves of one answer — so the whole thing is **`ApplyTemplatesRequest`** now (`templates: [{templateId, itemIds?}], estimate?`). Three rules: **`itemIds` absent or empty = the WHOLE bundle** (so the single-template endpoint and any older client are unchanged, and a bundle can never silently contribute nothing); the pick ORDER is kept (`distinct`, not a Set — it decides whose wording survives a duplicate); and **the subset is applied BEFORE the name de-dup**, so unticking a shared position in one bundle lets the NEXT bundle's copy through instead of dropping the line — the failure mode is silent and hits a bundle the master never touched. Keying the map on ids is safe because **`loadAccessible` does not fork** (unlike `loadWritable`).
